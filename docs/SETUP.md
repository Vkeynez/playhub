## Before you start

1. **Decide whose accounts these are (OPEN_QUESTIONS A0).** Every step below uses that identity: GitHub, Neon, Render, Google, Expo. The Android package and signing key are later bound to it for good.
2. **Use a separate browser profile** signed in only as that identity. That keeps it apart from work accounts on this Mac.
3. **Never paste a secret into the chat**, a commit, an issue or a screenshot. Secrets go straight from one dashboard into another. The table below says where each one lives.
4. **If this Mac's browser blocks a step** (for example GitHub refuses to create the repo because the browser is managed by your company), do that step on another device. Whether to push code from this Mac at all is your call. I don't push anything without your go-ahead.

### Where secrets live

| Secret | Created in | Stored in | Ever on this Mac? |
|---|---|---|---|
| Neon pooled and direct URLs (contain the DB password) | Neon (step 1) | Render env (step 3) | Only in your clipboard while you paste |
| GitHub fine-grained token | GitHub (step 2) | `~/.gamehub-secrets/github-token` (mode 600) | Yes, only if you want pushes from here |
| `JWT_SECRET`, `REFRESH_SECRET`, `K_ROTATE`, `ADMIN_TOKEN` | Generated by Render (`generateValue`) | Render env | No |
| Render deploy hook URL (web) | Render (step 3) | GitHub Actions secret `RENDER_WEB_DEPLOY_HOOK` | Only in your clipboard |
| Expo access token (push) | Expo (step 7) | Render env `EXPO_ACCESS_TOKEN` | Only in your clipboard |
| Release keystore | EAS servers (step 6) | EAS only | **Never** (OPEN_QUESTIONS G4) |
| FCM v1 service-account key | Firebase (step 7) | EAS credentials | Avoid: do it from a personal device |

Client IDs, SHA fingerprints, hostnames and project IDs are **not** secrets. Send those to me freely.

## 1. Neon (Postgres)

**When:** P0-M2, before the first Render deploy. **Why:** the API stores rooms, matches and accounts here (ARCHITECTURE §10.2).

1. Go to <https://console.neon.tech> and sign up with the A0 identity. The **Free** plan needs no card.
2. Click **New Project**.
   - **Project name:** `playhub`.
   - **Region:** **AWS Asia Pacific (Singapore)**, i.e. `aws-ap-southeast-1` *(label may differ)*. **The region can't be changed later.**
   - Under **Services**, expand **Postgres database** and set **Postgres version** to **17**. Leave the other services (object storage, functions, AI gateway, Neon Auth) off.
   - Click **Create project**.
3. **Cap the compute at 0.25 CU** (a bigger compute burns the 100 CU-hours faster):
   1. In the sidebar pick the default branch (`production`, or `main` on older projects), then **Computes**.
   2. On the primary compute click **Edit**.
   3. Choose **Autoscale** and drag **both** ends of the slider to **0.25** (min 0.25, max 0.25). Scale-to-zero after 5 min is fixed on Free; leave it on.
   4. Click **Save**.
4. **Set the same default for future branches:** **Settings → Postgres → Compute defaults → Modify defaults**, min 0.25 / max 0.25, **Save** *(label may differ)*.
5. **Copy both connection strings** (you'll paste them into Render in step 3; keep them only in your password manager until then):
   1. On the project dashboard click **Connect**.
   2. Turn **Connection pooling ON** and copy the string. Its host contains `-pooler`. This is **`DATABASE_URL`**.
   3. Turn **Connection pooling OFF** and copy again. Same host without `-pooler`. This is **`DATABASE_URL_DIRECT`**.
6. **Don't open the SQL Editor or Tables view "just to look".** Each visit wakes the compute and costs at least 5 min × 0.25 CU.

**Send back:** "Neon done", the region and the Postgres version shown on the dashboard.
**Never send:** either connection string (they contain the password).

## 2. GitHub

**When:** P0-M2. Render deploys from this repo, so it must exist before step 3.

### 2a. Create the repository

1. Go to <https://github.com/new> (signed in as `Vkeynez`).

3. **Don't** add a README, .gitignore or licence. The repo must be empty so the first push needs no merge.
4. Click **Create repository**.

> A public repo means the code is public. Secrets never go in git (only `.env.example`), and the online quiz bank stays out of git (OPEN_QUESTIONS I12).

### 2b. Actions settings

In the repo: **Settings → Actions → General** *(labels may differ)*:

1. **Actions permissions:** "Allow Vkeynez, and select non-Vkeynez, actions and reusable workflows", then tick **Allow actions created by GitHub**. Our workflows use only `actions/checkout`, `actions/setup-node` and `actions/cache`.
2. **Fork pull request workflows:** "Require approval for all external contributors".
3. **Workflow permissions:** **Read repository contents and packages permissions**. Leave "Allow GitHub Actions to create and approve pull requests" **unticked**.
4. Click **Save** in each section.

Optional but useful: **Settings → Rules → Rulesets → New branch ruleset** for `main` with "Require status checks to pass" → `lint, typecheck, test`. Add it after CI has run once, so the check name is listed.

### 2c. Fine-grained token (only if you want pushes from this Mac)

I never use `gh`, the macOS keychain or this machine's git credentials (CLAUDE.md). If you'd like me to push for you, create a token that can touch **only this repo**. Otherwise skip this and push yourself.

1. Open <https://github.com/settings/personal-access-tokens/new> (**Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**).
2. **Token name:** `playhub-push`. **Expiration:** 90 days or less.
3. **Resource owner:** `Vkeynez`. **Repository access:** **Only select repositories** → `playhub`.
4. **Repository permissions** (everything else stays "No access"):

   | Permission | Access | Why |
   |---|---|---|
   | Contents | Read and write | push commits and tags, upload release assets |
   | Workflows | Read and write | push changes under `.github/workflows/` |
   | Actions | Read and write | read CI logs, re-run a failed job |
   | Variables | Read and write | set `API_URL` for the keep-alive (step 8) |
   | Metadata | Read-only | required by GitHub (selected automatically) |

5. Click **Generate token** and copy it. GitHub shows it once.
6. **Save it on this Mac without it appearing on screen, in shell history or in the chat.** With the token still on the clipboard (from **Copy**), run this in Terminal. It writes the clipboard to the file, then clears the clipboard:

   ```bash
   (umask 077; mkdir -p ~/.gamehub-secrets; pbpaste | tr -d '[:space:]' > ~/.gamehub-secrets/github-token; pbcopy < /dev/null; wc -c < ~/.gamehub-secrets/github-token)
   ```

   The number printed should be about 93, the length of a fine-grained token. If it prints `0`, the clipboard was empty: copy the token again and re-run. (Pasting into a `read -s` prompt silently fails in some terminals, which is why this uses the clipboard.)

   The folder ends up `700` and the file `600`. To revoke later: same GitHub page → the token → **Delete**, then `rm ~/.gamehub-secrets/github-token`.
7. I'll use the token only for a push you've approved, through `scripts/isolated.sh`, and never print it.

**Send back:** the repo URL, and "token saved" or "no token, I'll push".
**Never send:** the token.

### 3d. Create the Blueprint

1. **New → Blueprint**, then **Connect** next to `playhub`.

   **If it shows a paid plan or Oregon, stop and tell me.**

   |---|---|
   | `DATABASE_URL` | Neon **pooled** string (host has `-pooler`) |

2. If the web URL isn't `https://playhub-web.onrender.com`: **playhub-api → Environment → `CORS_ORIGINS`** → set it to the real web URL → **Save** (this redeploys the API).

   ```bash
   curl -s https://playhub-api-nlgk.onrender.com/health
   ```

   Expect JSON containing `"ok":true`. An HTML page means it's still waking up; try again in a minute.
4. **Web deploy hook** (needed when I add the post-deploy workflow, ARCHITECTURE §10.6): **playhub-web → Settings → Deploy Hook** → copy. It's a secret. Store it straight into GitHub: **repo → Settings → Secrets and variables → Actions → Secrets → New repository secret**, name `RENDER_WEB_DEPLOY_HOOK`.
5. You can read `ADMIN_TOKEN` (for `/ops/*`) any time under **playhub-api → Environment**. Don't paste it into the chat.

**Rule (CLAUDE.md, OPEN_QUESTIONS G4):** release builds run **only on EAS cloud**. The release keystore is generated on EAS servers and never downloaded to this Mac.

### 6a. Account

1. Sign up at <https://expo.dev> with the A0 identity (Free plan; free accounts can't incur overages).
2. Create an organisation only if you want one; a personal account is fine.

### 6b. Link the project (`eas init`)

The global `eas-cli` on this Mac may be logged into a work account, so never use it. Pick one:

- **Option A, here, isolated (default):** run these in Terminal from the repo root. The wrapper gives Expo its own home folder (`.isolated/expo-home`, gitignored), so the work login is never seen. I'll tell you the exact `eas-cli` version to pin.

  ```bash
  scripts/isolated.sh npx --yes eas-cli@<pinned> login
  cd apps/client && ../../scripts/isolated.sh npx --yes eas-cli@<pinned> init
  ```

  `eas init` asks to create a project; accept. It writes the project ID into the app config. If the CLI complains about offline mode (the wrapper sets `EXPO_OFFLINE=1` for the Expo dev server), tell me.

### 6c. Release keystore (on EAS servers)

### 6d. Android client for release builds

In Google Cloud (step 5): **Clients → Create client → Android**, name `playhub android`, package `{{ANDROID_PACKAGE}}`, the **release SHA-1** from 6c → **Create**. Append its client ID to `GOOGLE_CLIENT_IDS` in Render (5e).

### 6e. App Links (`assetlinks.json`), strictly in this order

Android checks App Links **when the app is installed**, so the file must be live first (ARCHITECTURE §11):

### Private repo (only if you changed A3)

2. Tell me, and I'll delete the `schedule:` block from the workflow (keeping manual runs).

**Send back:** "keep-alive green" (or "cron-job.org set").

## 9. Custom domain (optional)

**When:** optional, but decide **before the first shared APK** (OPEN_QUESTIONS A8). The App Link host is baked into the APK, and Android 11 and older verify all hosts or none. A domain also makes cookie-mode auth possible (`*.onrender.com` is on the Public Suffix List).

1. Buy a domain at any registrar.
2. **playhub-web → Settings → Custom Domains → Add** → `example.com`. Render adds a `www` redirect automatically. Create the DNS records Render shows, then click **Verify**. Certificates are automatic.
3. **playhub-api → Settings → Custom Domains → Add** → `api.example.com` (a CNAME to the API's onrender.com host) → **Verify**.
4. Tell me the names. Then:
   - I update `CORS_ORIGINS` guidance, the CSP in `render.yaml`, the app config (`{{WEB_DOMAIN}}`) and `assetlinks.json`;
   - you add `https://example.com` to the Web client's origins and the authorised domains in Google (step 5), and update `API_URL` (step 8) and `CORS_ORIGINS` in Render.

**Send back:** the web and API domain names.
